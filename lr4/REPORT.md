## 1. Heap: структура данных

**Реализация:** [`src/heap.ts`](src/heap.ts).

### Инвариант и представление

Heap (двоичная куча) — это полное бинарное дерево, в котором каждый узел находится в заданном порядке со своими детьми. Если порядок «родитель ≤ дети» — это **min-heap** (наверху минимум), если «родитель ≥ дети» — **max-heap** (наверху максимум).

Полнота дерева (все уровни заполнены, кроме, возможно, последнего, который заполняется слева направо) позволяет хранить его в обычном массиве без указателей:

```
индекс узла i:
  левый потомок  = 2i + 1
  правый потомок = 2i + 2
  родитель       = (i - 1) >> 1
```

### Min-heap и max-heap — одна и та же структура

В коде нет двух отдельных классов. Есть один `Heap<T>` с инвариантом «`data[0]` — минимум по переданному компаратору», и две фабрики:

```ts
export function minHeap<T>(compare = numberOrder): Heap<T> {
  return new Heap<T>(compare);
}

export function maxHeap<T>(compare = numberOrder): Heap<T> {
  return new Heap<T>(reverse(compare)); // reverse(cmp)(a, b) = cmp(b, a)
}
```

Max-heap — это min-heap с инвертированным компаратором: тот, кто «минимален» по `reverse(compare)`, и есть максимум по `compare`. Один набор операций (`siftUp`/`siftDown`) обслуживает оба варианта, и ошибку в них придётся чинить только один раз.

### Операции

| Операция | Что делает | Время |
|---|---|---|
| `peek()` | вернуть `data[0]` | O(1) |
| `push(x)` | добавить в конец, поднять вверх (`siftUp`) | O(log n) |
| `pop()` | снять корень, переставить последний элемент на его место, опустить вниз (`siftDown`) | O(log n) |
| `new Heap(compare, array)` | построить кучу из готового массива | **O(n)**, не O(n log n) |

`siftUp`/`siftDown` идут по одному пути от корня к листу (или наоборот), а глубина дерева — ⌈log₂(n+1)⌉. Отсюда **O(log n)** на операцию.

### Почему построение кучи — O(n), а не O(n log n)

Интуитивно кажется, что раз высота дерева log n, а `siftDown` вызывается n/2 раз (для каждого внутреннего узла), то должно быть O(n log n). Это неверно: `siftDown` на узле высоты *h* стоит **O(h)**, а большинство узлов лежат близко к листьям, то есть имеют **маленькую** высоту. Число узлов на высоте *h* не больше ⌈n / 2^(h+1)⌉, поэтому суммарная работа:

```
Σ (h=0..log n) ⌈n / 2^(h+1)⌉ · O(h)  =  O(n · Σ h / 2^h)  =  O(n · 2)  =  O(n)
```

(ряд Σ h/2^h сходится к 2). Это известный результат (Cormen et al., «Build-Heap»), и он подтверждён измерением:

| n | Сравнений (heapify) | Отношение к n | Сравнений (n вставок, убывающий вход) | Отношение к n·log₂n |
|---:|---:|---:|---:|---:|
| 1 000 | 1 982 | 1.98 | 7 987 | 0.80 |
| 10 000 | 19 982 | 2.00 | 113 631 | 0.86 |
| 100 000 | 199 978 | 2.00 | 1 468 946 | 0.88 |
| 1 000 000 | 1 999 974 | 2.00 | 17 951 445 | 0.90 |

Отношение «сравнения / n» для `heapify` держится ровно на **2.0** на любом n — это и есть O(n). Отношение для вставки по одному элементу держится у **n·log₂n** — то есть на входе, который заставляет каждый новый минимум всплывать из листа в корень (убывающая последовательность), вставка по одному действительно даёт O(n log n). На n = 10⁶ это **9 раз больше сравнений**, чем bulk-heapify того же массива — разница между теорией и практикой здесь в 9x, а не в проценты.

(На случайном, а не специально подобранном входе вставка по одному в среднем почти линейна — большинству элементов некуда всплывать. Именно поэтому для замера взят убывающий вход: это тот конкретный случай, на котором оценка O(n log n) реализуется, а не просто верхняя граница, которая на практике никогда не достигается.)

### Сложность по памяти

Куча хранит элементы в одном массиве без дополнительных указателей — **O(n)**. Рекурсии нет (`siftUp`/`siftDown` — циклы), поэтому никакого стека вызовов — **O(1)** дополнительной памяти на операцию.

## 2. Пирамидальная сортировка (heap sort)

**Реализация:** [`src/heapSort.ts`](src/heapSort.ts).

### Алгоритм

1. Построить max-heap прямо в копии входного массива — O(n) (см. выше).
2. Пока куча не пуста: поменять местами корень (текущий максимум) с последним элементом кучи, уменьшить размер кучи на 1, восстановить инвариант (`siftDown` от корня).

```ts
for (let i = (n >> 1) - 1; i >= 0; i--) siftDown(data, i, n, desc);

for (let end = n - 1; end > 0; end--) {
  [data[0], data[end]] = [data[end]!, data[0]!];
  siftDown(data, 0, end, desc);
}
```

Куча и отсортированный суффикс массива живут **в одном и том же массиве**: на каждом шаге куча — это `data[0..end)`, а `data[end..n)` — уже готовый отсортированный хвост. Отдельная структура данных для кучи не нужна — поэтому используется экспортированный из `heap.ts` `siftDown`, а не класс `Heap<T>` целиком (класс добавил бы второй массив и был бы менее честным для O(1)-памяти).

### Сложность

| | O | Почему |
|---|---|---|
| Время, все случаи | **O(n log n)** | построение кучи O(n) + n извлечений по O(log n) |
| Память | **O(1)** дополнительной | не считая копии входа (как и `mergeSort` из лр3, функция не мутирует вход) |
| Стабильность | **нет** | перестановки при `siftDown` не сохраняют порядок равных элементов |

### Важное отличие от merge sort (ЛР №3)

У `mergeSort` из лр3 было оптимизация: если левая половина уже вся меньше правой, слияние пропускается, и на отсортированном входе получается **O(n)** вместо O(n log n). У heap sort такой лазейки нет: после построения кучи элементы лежат в *heap-порядке*, а не в отсортированном, и каждое из n извлечений всё равно требует полноценного `siftDown`. Проверено измерением: на **уже отсортированном** массиве из 100 000 элементов heap sort делает те же ~1.87·n·log₂n сравнений, что и на случайном массиве (3 112 517 сравнений против 3 020 005 на случайном) — никакого ускорения, лучшего случая у heap sort нет.

Зато есть то, чего нет у merge sort — **O(1) память**. Это главный практический повод выбрать heap sort: гарантированный O(n log n) без лишних аллокаций, когда объём данных ограничивает доступную память.

### Не стабилен — конкретный пример

Не просто «по определению», а на конкретном входе: сортируя людей по возрасту,

```ts
[{a,30}, {b,10}, {c,30}, {d,20}]  →  heapSort by age  →  [b(10), d(20), c(30), a(30)]
```

`c` оказывается раньше `a`, хотя в исходном массиве `a` шёл первым — порядок равных ключей не сохранён

## 3. Top-k сверху и снизу

**Реализация:** [`src/topK.ts`](src/topK.ts).

### Идея

Топ-k не требует сортировать весь массив — достаточно кучи размера **k**:

```ts
function selectK<T>(arr: readonly T[], k: number, compare: Comparator<T>): T[] {
  const heap = new Heap<T>(compare); // корень = самый слабый из уже отобранных кандидатов
  for (const value of arr) {
    if (heap.size < k) heap.push(value);
    else if (compare(value, heap.peek()!) > 0) {
      heap.pop();
      heap.push(value);
    }
  }
  const result: T[] = [];
  while (!heap.isEmpty) result.push(heap.pop()!);
  return result.reverse();
}
```

Куча на k элементов держит текущих «финалистов»; каждый новый элемент либо отбрасывается за одно сравнение (если он слабее худшего финалиста), либо меняется местами с ним за O(log k). `topKLargest` и `topKSmallest` — это один и тот же `selectK`, только второй вызывается с перевёрнутым компаратором (`reverse(compare)`), что даёт k *наименьших* вместо k *наибольших*. Дублировать логику не пришлось.

### Сложность

| | O |
|---|---|
| Время | **O(n log k)** |
| Память | **O(k)** |

При k ≪ n это существенно дешевле полной сортировки — O(n log n) по времени и O(n) по памяти. Измерение для k = 10:

| n | topK (куча), мс | Полная сортировка + slice, мс | Во сколько раз быстрее |
|---:|---:|---:|---:|
| 1 000 | 0.19 | 0.26 | 1.4× |
| 10 000 | 1.13 | 2.52 | 2.2× |
| 100 000 | 0.46 | 31.01 | 67.5× |
| 1 000 000 | 3.73 | 385.10 | 103× |
| 10 000 000 | 48.52 | 4 552.54 | 94× |

Разрыв растёт вместе с n — ожидаемо для O(n log k) против O(n log n), когда k зафиксирован, а n растёт.

Второе практическое преимущество кучи размера k, которого нет у полной сортировки: алгоритм **потоковый**. Он не требует держать весь массив в памяти одновременно — можно обрабатывать элементы по одному (например, из сетевого стрима) и в любой момент знать текущий топ-k, храня только k элементов.

## 4. Priority Queue

**Реализация:** [`src/priorityQueue.ts`](src/priorityQueue.ts).

Priority Queue — это ADT (абстрактный тип данных: «достань сначала самый приоритетный»), а Heap — его классическая реализация. Поэтому `PriorityQueue<T>` не содержит ни одной новой структурной операции — это обёртка над `Heap<T>` с более понятными именами:

```ts
export class PriorityQueue<T> {
  private readonly heap: Heap<T>;
  constructor(compare: Comparator<T>) { this.heap = new Heap<T>(compare); }
  enqueue(item: T): void { this.heap.push(item); }
  dequeue(): T | undefined { return this.heap.pop(); }
  peek(): T | undefined { return this.heap.peek(); }
}
```

Для самого частого случая — «элемент + числовой приоритет» — есть фабрика:

```ts
PriorityQueue.byPriority<Task>(task => task.priority) // по умолчанию: сначала самый приоритетный
```

```
const scheduler = PriorityQueue.byPriority<Task>(t => t.priority);
scheduler.enqueue({ task: 'fix prod outage', priority: 10 });
scheduler.enqueue({ task: 'reply to email',   priority: 1  });
scheduler.dequeue(); // 'fix prod outage'
```

Сложность enqueue/dequeue — та же, что у `push`/`pop` кучи: **O(log n)** время, **O(n)** память.

Отдельно стоит заметить: `byPriority` сравнивает не сами элементы `T` (которые могут быть Any), а числа, полученные через `priorityOf(item)`. Поэтому проблема «операции `>` `<` `===` не определены для Any», которая стоит в основе всего задания, здесь не возникает в принципе — она спроецирована в одно число, для которого всегда определён порядок (с той же оговоркой про NaN, см. ниже).

## 5. Number vs Any: как это закрыто типами

В задании два сценария: элементы — `Number` (операции `>`, `<`, `===` работают ожидаемо) или `Any` (не факт, что работают). Вместо двух параллельных реализаций это сделано одной сигнатурой с перегрузками:

```ts
export function minHeap<T extends number = number>(compare?: Comparator<T>): Heap<T>;
export function minHeap<T>(compare: Comparator<T>): Heap<T>;
```

```ts
minHeap<number>();                       // T = number: компаратор необязателен
minHeap<User>();                         // ошибка компиляции: нет перегрузки без компаратора
minHeap<User>((a, b) => a.age - b.age);  // T = User: компаратор обязателен и передан
```

Та же пара перегрузок — у `maxHeap`, `heapSort`, `topKLargest`, `topKSmallest`. Деление задания на «был на лекции / не был» превращается в проверку компилятора: забыл компаратор для не-number типа — код не соберётся, а не упадёт в рантайме на случайном входе.

### NaN: пример, почему «просто `<`/`>`» недостаточно даже для Number

Даже когда элементы — честные `number`, наивный компаратор ломается на `NaN`:

```ts
const naive = (a: number, b: number) => (a < b ? -1 : a > b ? 1 : 0);
naive(NaN, 5); // 0 — "равны". NaN < 5 и NaN > 5 оба false.
```

Компаратор обязан быть *тотальным порядком*: для любых a, b ровно одно из `a<b`, `a>b`, `a=b` истинно. `NaN` это нарушает — и наивный компаратор молча считает `NaN` «равным» любому числу, что портит инвариант кучи без единой ошибки или исключения: куча продолжит работать, но начнёт отдавать элементы в неправильном порядке, и заметить это можно только по итоговому результату.

`numberOrder` в [`src/compare.ts`](src/compare.ts) проверяет это явно и бросает исключение:

```ts
export const numberOrder: Comparator<number> = (a, b) => {
  if (Number.isNaN(a) || Number.isNaN(b)) {
    throw new TypeError(`numberOrder: NaN has no order (compare(${a}, ${b}))`);
  }
  return a < b ? -1 : a > b ? 1 : 0;
};
```

Упасть с понятной ошибкой на входе с `NaN` лучше, чем тихо вернуть неверно отсортированный массив — отсюда и название секции задания про Any: дело не только в объектах и смешанных типах, а в том, что даже «безопасный» Number не так уж безопасен без явной проверки.

## 6. Выводы

| Задача | Решение | Время | Память |
|---|---|---|---|
| Heap: push / pop / peek | бинарная куча на массиве | O(log n) / O(log n) / O(1) | O(n) |
| Heap: построение из массива | bottom-up heapify | **O(n)** | O(1) доп. |
| Пирамидальная сортировка | build-heap + n extract-max | O(n log n), **без лучшего случая** | O(1) доп. |
| Top-k (сверху/снизу) | куча размера k | O(n log k) | O(k) |
| Priority Queue | обёртка над Heap | O(log n) на операцию | O(n) |

Главный практический вывод: Heap — это одна структура с одним инвариантом, а не четыре разных алгоритма. Max-heap получается из min-heap инверсией компаратора, heap sort — это heap без обёртки класса (ради O(1) памяти), top-k — это heap фиксированного размера k, а Priority Queue — это heap с другими именами методов. Вся работа в lr4 свелась к тому, чтобы один раз правильно написать `siftUp`/`siftDown` и дальше переиспользовать их.
