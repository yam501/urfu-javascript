## 1. Почему точное хранение не проходит по памяти

Пусть **n** — число слов в словаре, **N** — суммарная длина всех слов в символах (N = Σ |word_i|, N ≥ n). Это естественная мера размера входных данных: именно столько памяти нужно, чтобы просто **хранить** слова как есть.

Любая структура, которая хранит слова точно (`Set<string>`, массив, trie, хеш-таблица с цепочками) — это, по теореме об информационной нижней границе, минимум **Θ(N)** памяти: чтобы отличить одно множество слов от другого, нужно где-то записать сами символы, а их суммарно N. Trie сжимает общие префиксы, но в худшем случае (словарь без общих префиксов) всё равно даёт Θ(N) узлов.

Задание требует памяти **строго меньше O(N)**. Для точной структуры это невозможно в принципе — значит, нужна структура, которая **не хранит слова**, а хранит *что-то меньшее*, из чего нельзя восстановить исходные слова обратно. Это Bloom filter.

## 2. Bloom filter

**Реализация:** [`src/bloomFilter.ts`](src/bloomFilter.ts).

### Идея

Битовый массив длины **m**. Чтобы добавить слово, вычисляем **k** позиций в массиве (через k разных хеш-функций) и выставляем там биты в 1. Чтобы проверить слово — проверяем те же k позиций:

- если хоть один бит = 0 → слова точно не было (**false negative невозможен**);
- если все k бит = 1 → слово *вероятно* было, но могло быть и совпадение чужих битов (**false positive возможен**).

```ts
add(word: string): void {
  const [h1, h2] = doubleHash(word);
  for (let i = 0; i < this.k; i++) {
    const index = (h1 + i * h2) >>> 0;
    this.setBit(index % this.m);
  }
  this.count++;
}
```

### k хеш-функций из двух (Kirsch–Mitzenmacher)

Вместо того чтобы писать k независимых хеш-функций, используется приём Kirsch–Mitzenmacher: берутся всего **две** хеш-функции `h1`, `h2` (здесь — FNV-1a с разными seed), а k позиций получаются как `h1 + i·h2 (mod m)` для `i = 0..k-1`. Доказано (Kirsch, Mitzenmacher, 2006), что по вероятности ложных срабатываний это не хуже, чем k независимых хешей, а считать нужно всего два хеша на слово вместо k.

```ts
function fnv1a(str: string, seed: number): number {
  let hash = (seed ^ 0x811c9dc5) >>> 0;
  for (let i = 0; i < str.length; i++) {
    hash ^= str.charCodeAt(i);
    hash = Math.imul(hash, 0x01000193);
  }
  return hash >>> 0;
}

function doubleHash(word: string): readonly [number, number] {
  return [fnv1a(word, 0), fnv1a(word, 0x9e3779b9)];
}
```

### Битовая упаковка — почему это важно, а не просто стиль

Биты хранятся в `Uint32Array`, по 32 бита на ячейку (`bits[i >>> 5] |= 1 << (i & 31)`), а не в `Uint8Array` или обычном массиве `boolean[]`. Это не стилистический выбор: `Uint8Array` с одним байтом на бит сразу съедает **в 8 раз больше** памяти, чем нужно, а обычный массив — боксированные JS-числа — все выгоды обесценивает мгновенно (объект на каждый бит, десятки байт вместо одного). Если бы здесь была ошибка упаковки, вся история про «меньше O(N)» развалилась бы на первом же замере — именно поэтому `byteLength` структуры сверен с теоретической формулой в разделе 4.

## 3. Функциональные требования

**Реализация:** [`src/dictionary.ts`](src/dictionary.ts) — тонкая обёртка над `BloomFilter` (та же связка, что `PriorityQueue`/`Heap` в лр4: вся алгоритмика — в generic-структуре, обёртка только называет операции так, как они сформулированы в задании):

| Требование | Метод |
|---|---|
| Добавление 1 слова | `addWord(word: string): void` |
| Добавление списка слов | `addWords(words: Iterable<string>): void` |
| Проверка существования слова | `has(word: string): boolean` |

```ts
const dict = Dictionary.fromWordList(words, 0.01); // список известен заранее — точный размер
// или:
const dict = new Dictionary(expectedWordCount, 0.01); // слова добавляются по одному со временем
dict.addWord('привет');
dict.addWords(['мир', 'тест']);
dict.has('привет'); // true
```

`addWord` и `addWords` не различаются по гарантиям: `addAll` — это просто цикл по `add`, и поскольку установка бита (`|=`) не зависит от порядка, результат идентичен бит в бит независимо от того, добавлены слова по одному или пакетом.

## 4. Сложность по времени и памяти, ведущие множители

### Время

| Операция | Время | Почему |
|---|---|---|
| `addWord(w)` | **O(\|w\| + k)** | один проход по символам слова для хеша + k констант обращений к битовому массиву |
| `has(w)` | **O(\|w\| + k)** | то же самое |
| `addWords(list)` | **O(T + m·k)** | T — суммарная длина слов в списке, m — число слов в списке |

k — число хеш-проб — не зависит ни от n, ни от длины слова, это константа, определяемая только целевой вероятностью ошибки (см. таблицу ниже). Поэтому время операции по сути **O(длина слова)** — быстрее в принципе невозможно, слово нужно хотя бы прочитать целиком.

### Память — и вот её ведущий множитель

Оптимальные параметры (минимизация m при заданных n и вероятности ложного срабатывания p):

```
m = -n·ln(p) / (ln 2)²        — число бит
k = (m/n)·ln 2                 — число хеш-проб
```

Код: [`optimalBitCount`, `optimalHashCount`](src/bloomFilter.ts). Ключевое свойство: **m зависит только от n и p — не от длины слов**. Если задание просит явно указать ведущий множитель в форме O(M), M = c·N — вот он, посчитанный, а не просто «O(n)»:

| Целевая вероятность ошибки p | Бит/элемент | Байт/элемент | k (хеш-проб) |
|---:|---:|---:|---:|
| 10% | 4.79 | 0.60 | 3 |
| **1%** | **9.59** | **1.20** | **7** |
| 0.1% | 14.38 | 1.80 | 10 |
| 0.01% | 19.17 | 2.40 | 13 |

(9.6 бит/элемент при p=1% — известная константа из литературы по Bloom-фильтрам, совпадает с расчётом по формуле.)

Итого: при p = 1% память — это **M ≈ 1.2·n байт**, то есть **O(M), M = 1.2·N_слов** (где N_слов — число слов, а не суммарная длина символов). Это напрямую следует из формулы: `m` зависит только от `n` и `p`, длина слов туда не входит — при хранении слов длиной 1 символ и длиной 500 символов фильтр займёт одинаковое число байт.

### Замер: во сколько раз это меньше наивного хранения

`npm run bench` сравнивает `Dictionary` с обычным `Set<string>` на случайных словах длиной 3–12 символов (точный замер байт у Bloom filter — `byteLength`; у `Set` — приближённый, по `process.memoryUsage().heapUsed` с форсированным GC, что по природе шумнее):

| n | Средняя длина слова | `Set`, байт/слово (≈) | Bloom filter, байт/слово (точно) | Во сколько раз меньше |
|---:|---:|---:|---:|---:|
| 10 000 | 7.4 | ≈13.6 | 1.20 | ≈11× |
| 100 000 | 7.5 | ≈26.5 | 1.20 | ≈22× |
| 1 000 000 | 7.5 | ≈21.0 | 1.20 | ≈18× |

(На n = 1 000 сигнал тонет в шуме GC — измерение показательно только начиная с десятков тысяч элементов, поэтому эта строка не приводится.)

~20–30 байт на короткое слово в `Set<string>` — это объектные накладные расходы V8 (заголовок строки, запись в хеш-таблице Set, UTF-16) поверх самих символов, и это тот самый порядок величины, который в условии задания фигурирует как пример «M = 33·N»: обычная структура данных платит десятки байт константных накладных расходов на каждый элемент, а Bloom filter — чуть больше одного байта, вне зависимости от длины слова.

## 5. В каком смысле это «меньше O(N)»

Здесь нужна аккуратность, а не лозунг. Если N — суммарная длина слов, а средняя длина слова **ограничена константой** (как в любом естественном языке — скажем, не длиннее 50 символов), то формально N = Θ(n): оба растут линейно по числу слов, и в этом узком асимптотическом смысле «O(n) бит у Bloom filter» и «O(n) байт у наивного хранения» — один и тот же порядок роста, различающийся только константой (в замере выше — на 11–22×).

Асимптотическое (не только константное) преимущество проявляется, если снять это искусственное ограничение и позволить длине слов расти: тогда N = Θ(n·L̄), где L̄ — средняя длина слова, и если L̄ растёт (например, словарь строится не из слов языка, а из URL, хешей, предложений произвольной длины), наивное хранение растёт как Θ(n·L̄), а Bloom filter остаётся **Θ(n)** — ведущий множитель вообще не зависит от L̄. Вот это — уже разный класс роста, строго `o(N)`, а не просто «тот же O(n) с меньшей константой».

Для реальной задачи — словарь языка с ограниченной длиной слов — честная формулировка такая: **памяти O(n) бит с константой ~1.2 байта/слово (p=1%), что на практике в 10–20 раз меньше**, чем у любой структуры, хранящей слова как строки. Строгое асимптотическое «меньше O(N)» — там, где N позволяют расти вместе с длиной элементов.

## 6. Выводы

| | O | Ведущий множитель |
|---|---|---|
| `addWord` / `has` | O(длина слова) | + k хеш-проб, k — константа от p |
| `addWords(список)` | O(суммарная длина списка) | |
| Память | O(n) бит | ~9.6 бит/слово при p=1%, не зависит от длины слов |

Главный вывод не в том, что «Bloom filter экономит память» само по себе, а в том **откуда** эта экономия берётся: структура принципиально выбрасывает информацию о содержимом слов (восстановить слово по биту невозможно) и платит за это управляемой, но ненулевой вероятностью ошибки. Это первая лаба из всех пяти, где корректность — не бинарная гарантия, а вероятность, которую нужно явно считать, закладывать в размер структуры заранее и мониторить по мере роста словаря (`estimatedFalsePositiveRate`).
