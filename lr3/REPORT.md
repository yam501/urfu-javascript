Все алгоритмы — generic-функции, которые принимают компаратор `(a: T, b: T) => number` (тот же контракт, что у `Array.prototype.sort`). Поэтому они работают с любыми типами, а не только с числами:

mergeSort(users, (a, b) => a.age - b.age);

## 2. Сортировка массива

**Алгоритм:** сортировка слиянием (top-down merge sort) — [`src/sort.ts`](src/sort.ts).

### Почему слияние, а не quicksort

| | Merge sort | Quicksort | `Array.prototype.sort` (V8, TimSort) |
|---|---|---|---|
| Худший случай | **O(n log n)** | O(n²) | O(n log n) |
| Лучший случай | **O(n)** * | O(n log n) | O(n) |
| Память | O(n) | O(log n) | O(n) |
| Стабильность | **да** | нет | да |

\* благодаря оптимизации, описанной ниже.

Merge sort гарантирует O(n log n) на любых данных и стабилен, то есть равные элементы сохраняют исходный порядок. Это важно, например, при сортировке таблицы сначала по одной колонке, потом по другой. Встроенный в V8 TimSort тоже построен на слиянии.

### Реализация

```ts
function sortRange<T>(a: T[], buf: T[], lo: number, hi: number, cmp: Comparator<T>): void {
  if (hi - lo < 2) {
      return;
  }
  const mid = (lo + hi) >>> 1;
  sortRange(a, buf, lo, mid, cmp);
  sortRange(a, buf, mid, hi, cmp);
  if (cmp(a[mid - 1]!, a[mid]!) <= 0) {
      return;   // половины уже упорядочены
  }
  merge(a, buf, lo, mid, hi, cmp);
}
```

Особенности:
- **Один буфер на всю сортировку.** Буфер выделяется один раз, а не на каждом слиянии: `n` элементов памяти вместо `n log n` аллокаций и меньше работы для GC.
- **Пропуск слияния.** Если последний элемент левой половины ≤ первого элемента правой, половины уже идут по порядку и сливать их не нужно. На отсортированном входе это даёт **O(n)**.
- **Чистая функция.** Входной массив не мутируется (`readonly T[]` в сигнатуре).

### Анализ сложности

**Время.** Рекуррентное соотношение:

```
T(n) = 2·T(n/2) + Θ(n)
```

По основной теореме (a = 2, b = 2, f(n) = Θ(n) = Θ(n^log_b a)) получаем **T(n) = Θ(n log n)**.

Интуитивно: дерево рекурсии имеет высоту ⌈log₂ n⌉, и на каждом уровне суммарно сливается n элементов.

| Случай | Сравнений | O |
|---|---|---|
| Худший / средний | ≈ n·log₂ n − n + 1 | **O(n log n)** |
| Лучший (вход отсортирован) | ровно n − 1 | **O(n)** |

**Память:** O(n) на буфер + O(log n) на стек рекурсии = **O(n)**.

### Эмпирическая проверка

`npm run bench` подсчитывает реальное число вызовов компаратора:

| n | Сравнений (случайный вход) | Отношение к n·log₂ n | Сравнений (отсортированный вход) | Время, мс |
|---:|---:|---:|---:|---:|
| 1 000 | 9 410 | 0.944 | 999 | 0.87 |
| 10 000 | 127 444 | 0.959 | 9 999 | 2.75 |
| 100 000 | 1 605 661 | 0.967 | 99 999 | 33.62 |
| 1 000 000 | 19 339 758 | 0.970 | 999 999 | 454.15 |

- Отношение `сравнения / (n·log₂ n)` почти постоянно (~0.95–0.97), то есть рост действительно n log n. К 1 оно приближается снизу из-за слагаемого −n в формуле худшего случая.
- На отсортированном входе ровно **n − 1** сравнений, лучший случай O(n) подтверждён.

## 3. Бинарный поиск

**Реализация:** [`src/binarySearch.ts`](src/binarySearch.ts).

Ищется не «любое вхождение», а **lower bound**: первый индекс `i`, для которого `arr[i] >= target`. Поиск строится поверх него:

```ts
export function lowerBound<T>(sorted: readonly T[], target: T, compare = naturalOrder): number {
  let lo = 0;
  let hi = sorted.length;          // полуинтервал [lo, hi)
  while (lo < hi) {
    const mid = (lo + hi) >>> 1;
    if (compare(sorted[mid]!, target) < 0) lo = mid + 1;
    else hi = mid;
  }
  return lo;
}

export function binarySearch<T>(sorted: readonly T[], target: T, compare = naturalOrder): number {
  const i = lowerBound(sorted, target, compare);
  return i < sorted.length && compare(sorted[i]!, target) === 0 ? i : -1;
}
```

Почему так, а не классический вариант с `if (arr[mid] === target) return mid`:
- **Детерминированный результат при дубликатах.** Всегда возвращается *первое* вхождение (как у `indexOf`), а классический вариант вернёт случайное из них.
- **Точка вставки бесплатно.** `lowerBound` сразу говорит, куда вставить элемент, чтобы массив остался отсортированным. Это пригодится для автокомплита, виртуализированных списков и поиска по таймлайну.
- **Полуинтервал `[lo, hi)`** убирает типичные ошибки на ±1 с границами.
- **`(lo + hi) >>> 1`** — целочисленное деление на 2 без `Math.floor`. Длина JS-массива не превышает 2³² − 1, поэтому беззнаковый сдвиг безопасен.

### Анализ сложности

После каждой итерации длина интервала `hi − lo` уменьшается как минимум вдвое. После k итераций она не больше n / 2ᵏ, поэтому цикл завершается не более чем за **⌊log₂ n⌋ + 1** итераций. Плюс одно сравнение на равенство в `binarySearch`.

| | O |
|---|---|
| Время (любой случай) | **O(log n)** |
| Память | **O(1)** |

У lower-bound варианта нет «раннего выхода», поэтому лучший случай тоже O(log n). Это осознанный компромисс ради предсказуемого результата при дубликатах.

**Предусловие:** массив отсортирован тем же компаратором, иначе результат не определён. Если массив нужно сначала отсортировать, это стоит O(n log n). Бинарный поиск окупается при множестве запросов: k запросов обойдутся в O(n log n + k log n) против O(k·n) у линейного поиска.

### Эмпирическая проверка

Максимум сравнений по 10 000 случайных запросов:

| n | Макс. сравнений | Теория: ⌈log₂(n+1)⌉ + 1 |
|---:|---:|---:|
| 1 000 | 11 | 11 |
| 10 000 | 15 | 15 |
| 100 000 | 18 | 18 |
| 1 000 000 | 21 | 21 |
| 10 000 000 | 25 | 25 |

Совпадение с теорией точное. При росте n в 10 000 раз число шагов выросло всего с 11 до 25.

## 4. Баланс скобок

**Реализация:** [`src/brackets.ts`](src/brackets.ts). Поддерживаются `()`, `[]`, `{}`, `<>`.

### Идея

Последняя открытая скобка должна закрыться первой, то есть это порядок **LIFO**, и естественная структура для него — **стек**:
- открывающая скобка → кладём в стек;
- закрывающая → снимаем вершину стека; если стек пуст или скобка другого типа, ошибка;
- в конце стек должен быть пуст, иначе остались незакрытые скобки.

Остальные символы игнорируются, поэтому функция работает на реальном коде:

```
f(a[i]) { return <T>x; }   ✓
```

### Типизация

Пары скобок заданы одной константой, а типы выводятся из неё. Так не нужно поддерживать отдельные списки «открывающих» и «закрывающих» символов:

```ts
const PAIRS = { ')': '(', ']': '[', '}': '{', '>': '<' } as const;

type Closer = keyof typeof PAIRS;          // ')' | ']' | '}' | '>'
type Opener = (typeof PAIRS)[Closer];      // '(' | '[' | '{' | '<'
```

Функция возвращает не просто `boolean`, а **discriminated union** с описанием ошибки:

```ts
type BracketError =
  | { kind: 'unexpected'; index: number; found: Closer }
  | { kind: 'mismatch';   index: number; found: Closer; expected: Closer; openedAt: number }
  | { kind: 'unclosed';   index: number; expected: Closer };
```

В CLI `switch` по `kind` проверяется компилятором на полноту: если добавить новый вид ошибки и не обработать его, сборка упадёт. На основе этих данных CLI рисует диагностику в стиле компилятора:

```
$ npm run brackets -- "({)}" "[<>]{" "())"
✗ ({)}
   ~^ expected '}' (opened at 1), found ')'
✗ [<>]{
      ^ unclosed bracket, expected '}' before end of input
✗ ())
    ^ unexpected ')': nothing to close
```

`~` показывает, где скобка была открыта, `^` — где обнаружена ошибка.

### Оптимизация: в стеке только индексы

В первой версии стек хранил объекты `{ char, index }`. Это означало аллокацию на каждую скобку и нагрузку на GC. Теперь в стеке лежат только индексы (`number[]`), а сам символ берётся как `input[index]`. V8 хранит такой массив как плотный массив малых целых чисел (packed SMI) без отдельных объектов в куче.

| n = 10⁷ | Время |
|---|---:|
| Стек объектов | ~1055 мс |
| Стек индексов | ~390–455 мс |

Ускорение примерно **в 2.5 раза**, при этом асимптотика не изменилась.

### Анализ сложности

| | O | Пояснение |
|---|---|---|
| Время | **O(n)** | один проход; на символ O(1): `Object.hasOwn` по 4 ключам, амортизированные `push`/`pop` |
| Память | **O(n)** в худшем случае | вход `((((((…` целиком попадает в стек |
| Ранний выход | да | на первой ошибке |

### Эмпирическая проверка

| n | Время, мс | нс на символ |
|---:|---:|---:|
| 1 000 | 0.34 | 336.9 |
| 10 000 | 1.46 | 146.4 |
| 100 000 | 4.86 | 48.6 |
| 1 000 000 | 48.83 | 48.8 |
| 10 000 000 | 455.70 | 45.6 |

Начиная с n = 10⁵ время на символ постоянно (~45–50 нс), рост линейный. На малых n доминируют фиксированные накладные расходы: вызов функции, разрешение таймера и прогрев JIT.

## 5. Тестирование

24 теста, `npm test`. Помимо обычных unit-тестов на граничные случаи, используется **property-based тестирование** (fast-check): библиотека генерирует сотни случайных входов и проверяет **инварианты**, а не конкретные значения.

| Свойство | Как проверяется |
|---|---|
| `mergeSort` корректна | результат совпадает с `Array.prototype.sort` на любом массиве |
| `mergeSort` стабильна | у равных ключей сохраняется исходный порядок |
| `binarySearch` корректен | совпадает с `indexOf` на любом отсортированном массиве |
| `lowerBound` корректен | все элементы левее `< x`, все правее `>= x` |
| Все сбалансированные строки принимаются | строки генерируются по грамматике `S → ε \| (S)S` |
| Порча ломает баланс | удаление любого одного символа из сбалансированной строки делает её несбалансированной |

При падении fast-check автоматически **минимизирует** контрпример (shrinking) до самого короткого входа, на котором воспроизводится ошибка.

## 6. Выводы

| Задача | Алгоритм | Время | Память |
|---|---|---|---|
| Сортировка | merge sort | O(n log n), лучший O(n) | O(n) |
| Поиск | binary search (lower bound) | O(log n) | O(1) |
| Баланс скобок | стек | O(n) | O(n) |

Все теоретические оценки подтверждены измерениями: число сравнений в сортировке растёт как n log n, число шагов поиска точно совпадает с ⌈log₂(n+1)⌉ + 1, проверка скобок работает за линейное время.

Отдельно отмечу, что асимптотика — не вся картина. Константа тоже важна: замена объектов на числа в стеке не изменила O(n), но ускорила проверку скобок в 2.5 раза.
