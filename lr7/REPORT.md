## 1. Структура данных

Структура — [`src/tree.ts`](src/tree.ts). Узел знает ровно две вещи: своё значение и упорядоченный список потомков (`children`). Это максимум, что нужно любому обходу, и минимум, без которого связь «родитель — потомки» не существует. Интерфейс `TreeLike<T>` описывает только эту пару, класс `TreeNode<T>` её реализует, обходы принимают `TreeLike` — то есть работают на любой структуре, у которой нашлись значение и потомки, а не только на этом конкретном классе.

Потомки — именно список, а не пара `left`/`right`: бинарное дерево получается как частный случай (k ≤ 2 потомков), а обходы пишутся один раз для произвольного k. Порядок списка — порядок «слева направо», в котором обходы обязаны посещать братьев.

В том же файле — генераторы деревьев для проверки: `node()` строит дерево из вложенного литерала, `chain(depth)` — цепочку глубиной depth (максимально глубокое дерево при данном числе узлов), `randomTree(n, seed)` — случайное дерево из n узлов с детерминированным ГПСЧ, чтобы прогоны повторялись.

## 2. BFS через очередь

Обход в ширину — [`traversals.ts`](src/traversals.ts), `bfs`. Очередь узлов: снять узел с головы, выдать значение, потомков — в хвост. Так узлы выдаются уровень за уровнем, внутри уровня — слева направо.

Деталь реализации: очередь — массив с указателем головы (`for (let head = 0; head < queue.length; head++)`), а не `Array.shift()`. `shift()` перекладывает весь хвост массива на каждый вызов, и обход n узлов из O(n) превращается в O(n²). Указатель головы даёт амортизированный O(1) на снятие: прочитанный элемент остаётся лежать в массиве, но больше никогда не читается.

## 3. DFS preorder через стек

Прямой порядок — `dfsPreorder`. Цикл из трёх шагов: снять узел с вершины стека, сразу выдать его значение, положить потомков. Значение выдаётся до потомков — это и есть preorder. Потомки кладутся в обратном порядке (от последнего к первому), потому что стек снимает в LIFO: положенные слева направо снимались бы справа налево, и братья шли бы в обратном порядке.

Рекурсивный preorder делает то же самое неявно: «выдать значение, затем рекурсивно обойти потомков» — его стек вызовов и есть этот стек, только невидимый.

## 4. DFS postorder через два стека

Обратный порядок — `dfsPostorder`, схема «два стека». Первый стек работает как в preorder с одной разницей: потомки кладутся в прямом порядке. Итог первого цикла — последовательность, в которой каждый узел стоит раньше своих потомков, а поддеревья старших братьев — раньше поддеревьев младших. Разворот этой последовательности меняет оба отношения на противоположные: потомок раньше предка, младшие братья раньше старших — а это в точности определение postorder. Роль «второго стека» играет массив результата, который в конце переворачивается (`out.reverse()`).

Альтернатива — один стек с указателем на последнего выданного узла и проверкой «все ли потомки уже выданы». Схема с переворотом выбрана потому, что это те же шесть строк, что и preorder, и корректность сводится к одному рассуждению про разворот, а не к аккуратной работе с флагами состояний.

## 5. DFS inorder: обобщение на n потомков и стек кадров

Симметричный порядок — единственный из четырёх, для которого нужен дополнительный механизм, и причина вот в чём. В preorder и postorder значение узла выдаётся в фиксированной точке относительно всех потомков сразу (до всех / после всех) — достаточно стека самих узлов. В inorder значение узла выдаётся **между** потомками: левое поддерево, узел, правое поддерево. Стек должен помнить, в какого потомка узел уже спускался, — самих ссылок на узлы для этого мало.

### Обобщение

Классический inorder определён для бинарного дерева. Наша структура допускает любое число потомков k, поэтому нужно соглашение, где узел встаёт между k потомками. Выбрано такое: **узел выдаётся после первых ⌊k / 2⌋ потомков**. При k = 2 это в точности классическое «лево — узел — право», у листа (k = 0) — просто выдача узла, при нечётном k узел встаёт в середину из k + 1 позиций. Единого канона для n-арного inorder в литературе нет; этот вариант выбран потому, что при k = 2 он совпадает с классическим и симметричен относительно середины.

Проверка того, что обобщение не расходится с классикой: на полном бинарном дереве (у каждого внутреннего узла ровно 2 потомка) обобщённый inorder обязан совпадать с классическим, а классический inorder бинарного дерева поиска обязан давать отсортированный ряд. Прогон на полном BST из значений 1..15 даёт ровно `1, 2, ..., 15` — совпадает.

### Стек кадров

Реализация — `dfsInorder`. Стек хранит не узлы, а кадры — объекты `{ node, next, mid, emitted }`. Кадр — это явный аналог кадра стека вызовов рекурсивной версии: `node` — в каком узле находимся, `next` — в чьё поддерево спускаемся следующим, `mid` = ⌊k / 2⌋ — перед каким потомком наступает очередь самого узла, `emitted` — выдано ли уже значение. Цикл смотрит только на верхний кадр и делает ровно одно из трёх:

1. `next === mid` и значение ещё не выдано — выдать значение узла (середина пройдена);
2. есть непосещённые потомки — спуститься: `next++`, положить кадр потомка;
3. потомков не осталось — снять кадр (возврат из рекурсии).

Инвариант: кадры на стеке — это в точности узлы текущего пути от корня, по кадру на каждый. Глубина стека равна высоте дерева, а не числу узлов.

Пример — дерево из `bench.ts`:

```
A
├─ B
│  ├─ E
│  └─ F
│     └─ I
├─ C
└─ D
   ├─ G
   └─ H
```

| Обход | Результат |
|---|---|
| BFS | `A B C D E F G H I` |
| DFS preorder | `A B E F I C D G H` |
| DFS inorder | `E B F I A C G D H` |
| DFS postorder | `E I F B C G H D A` |

Inorder читается так: у A трое потомков, mid = 1 — сначала поддерево B (`E B F I`: у B двое, mid = 1, поэтому E, потом сам B, потом поддерево F, где F с единственным потомком встаёт перед ним), затем сам A, затем C и поддерево D (`G D H`).

## 6. Почему запрет рекурсии — не формальность

У стека вызовов фиксированный размер (в Node.js по умолчанию меньше мегабайта, ~10⁴ кадров), и рекурсивный обход падает с `RangeError` на любом достаточно глубоком дереве, хотя дерево абсолютно корректно. Явный стек живёт в куче и ограничен только доступной памятью.

Замер из `bench.ts` (рекурсивный эталон на цепочках):

| Глубина цепочки | Рекурсивный preorder |
|---|---|
| 1 000 | проходит |
| 10 000 | `RangeError` — стек вызовов исчерпан |
| 100 000 | `RangeError` |

Итеративные обходы на цепочке из **1 000 000** узлов проходят все четыре (таблица времен ниже). Рекурсивная версия не может обработать дерево в сто раз меньше.

## 7. Сложность

Время у всех четырёх обходов O(n): каждый узел кладётся и снимается ровно один раз, каждое ребро проходится один раз.

Дополнительная память различается, и это единственное содержательное отличие между обходами:

| Обход | Вспомогательная память | Что именно хранится |
|---|---|---|
| BFS | O(w), где w — ширина дерева | очередь: не больше двух соседних уровней |
| DFS preorder | O(h) при фиксированной степени, O(n) в худшем | стек непосещённых младших братьев узлов текущего пути |
| DFS postorder | как preorder + массив результата | тот же стек; результат — это выход, а не служебная память |
| DFS inorder | O(h) строго | по одному кадру на узел текущего пути |

Здесь h — высота, w — ширина (размер самого широкого уровня). У BFS и DFS худшие случаи зеркальны: у цепочки w = 1, h = n (DFS живёт, BFS-очередь мизерная, зато DFS-стек — весь путь), у звезды (корень и n − 1 лист) w = n, h = 2 (у BFS очередь — весь уровень листьев, зато DFS-стек при обработке корня держит всех его потомков, то есть тоже O(n)). Стек preorder/postorder хранит непосещённых братьев вдоль текущего пути: при фиксированной степени ветвления их O(1) на уровень, отсюда O(h); у звезды все n − 1 братьев лежат одновременно.

## 8. Проверка

`npm run bench`, четыре блока.

**Сверка с эталоном.** В `bench.ts` написаны рекурсивные версии всех четырёх обходов — только как независимый оракул для проверки; в `traversals.ts` рекурсии нет. 300 случайных деревьев по 1–300 узлов, все четыре обхода: **300/300 совпадений**. Для inorder оракул проверяет механику явного стека (тот же порядок должен получаться без единой ошибки в `next`/`mid`/`emitted`), а само соглашение «после первых ⌊k/2⌋ потомков» проверяется отдельно — полнотой BST из раздела 5. Пустой корень (`null`, `undefined`) во всех четырёх обходах даёт `[]`.

**Предел стека вызовов** — раздел 6: рекурсия падает между 1 000 и 10 000 глубины, итеративные обходы проходят 1 000 000.

**Времена на 1 000 000 узлов** (лучший из 3 прогонов, Node.js, `performance.now`):

| Дерево | bfs, мс | preorder, мс | inorder, мс | postorder, мс |
|---|---:|---:|---:|---:|
| случайное 10⁶ узлов | 170.06 | 200.22 | 317.78 | 194.70 |
| цепочка 10⁶ узлов | 49.82 | 38.96 | 94.03 | 38.63 |

Inorder в 1.6–2.4 раза медленнее остальных: вместо ссылки на узел стек гоняет объект-кадр, и на каждой итерации выбирается одна из трёх веток. Цепочка быстрее случайного дерева на порядок по константе: у каждого узла один потомок, массивы `children` длины ≤ 1 лежат в памяти подряд. Все четыре остаются O(n) — на цепочке это видно чище всего: время пропорционально только числу узлов.

## 9. Выводы

Все четыре обхода реализованы на одной структуре «значение + упорядоченный список потомков» и без рекурсии. Три из них сводятся к очереди или стеку узлов: BFS — очередь с указателем головы (без O(n²)-`shift`), preorder — стек с укладкой потомков в обратном порядке, postorder — тот же стек в прямом порядке плюс разворот результата. Inorder потребовал перейти от стека узлов к стеку кадров, потому что значение узла выдаётся между потомками, и позицию между ними надо хранить явно; кадры — это стек вызовов рекурсивной версии, перенесённый в кучу.

Запрет рекурсии оказался не стилистическим ограничением, а диапазоном применимости: рекурсивная версия падает на глубине порядка 10⁴ узлов, итеративные проходят миллион. Разница в памяти между обходами тоже содержательная: BFS платит за ширину дерева, DFS — за высоту, и худшие случаи у них зеркальные.
